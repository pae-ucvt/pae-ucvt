Теория на сегодня
1. Зачем нужны мультиагентные системы
Что мы сегодня узнаем↘️
•	Когда одного агента уже недостаточно.
•	Три модели работы: последовательно, параллельно, по ролям.
•	Что такое subagents в Claude Code.
•	Где проходит граница пользы.
•	Как применить подход к своему проекту.
Когда одного агента недостаточно ↘️
Мы много можем сделать при помощи одного агента — изучить скиллы, подключить разные коннекторы в виде MCP. Тем не менее несколько агентов нам нужны вовсе не для красоты, а чтобы разделить ответственность, когда у нас есть разные типы задач: например, поиск информации, написание, редактура и валидация финального результата.
Важно не количество агентов, а управляемость результата и то, что мы получаем на выходе.
Если в ваших задачах один агент справляется быстро, выполняет конкретную задачу и даёт понятный, измеримый результат — усложнять не стоит. Но если задача приобретает характер многофазности и многоступенчатости, тогда можно задуматься о субагентах.
2. Три модели взаимодействия агентов
Последовательная модель ↘️
✅
Последовательная модель — когда у нас есть задача, состоящая из определённых этапов, и каждый последующий этап зависит от предыдущего. Это может работать медленнее, чем другие мультиагентные системы, но это абсолютно рабочий и понятный подход.
Пример последовательной модели:
•	Запрос пользователя
•	Агент-исследователь собирает факты
•	Агент-редактор превращает факты в структурированный текст
•	Агент-проверяющий ищет ошибки
•	Финальный результат
Запрос пользователя
→ Агент-исследователь собирает факты
→ Агент-редактор превращает вывод в понятный ответ
→ Агент-проверяющий ищет ошибки
→ Финальный результат
Параллельная модель ↘️
✅
Параллельная модель — задача разделяется на составные части, которые можно выполнять одновременно. Несколько субагентов работают параллельно и возвращают результаты главному агенту. Это позволяет работать быстрее.
⚠️
Параллельная модель чуть сложнее: результаты могут быть несогласованными. Необходим чёткий контракт — формат, в котором агенты получают задачи и возвращают результаты.
Пример параллельной модели:
•	Один запрос
•	Агент А ищет официальное определение, агент Б — практические примеры, агент В — риски и ограничения
•	Все результаты возвращаются главному агенту или агенту-агрегатору
•	Финальный результат
Запрос пользователя
├─ Агент A: ищет официальное определение
├─ Агент B: ищет практические примеры
└─ Агент C: ищет риски и ограничения
        ↓
Агент-агрегатор объединяет результат
        ↓
Финальный ответ
Ролевая модель ↘️
✅
Ролевая модель — у каждого агента есть чётко заданная роль: ресёрчер (исследователь), аналитик, райтер (автор), ревьюер (проверяющий). Роли прописываются заранее.
💡
Лишние роли усложняют процесс без пользы — не нагромождайте агентов без необходимости.
Три модели не исключают друг друга — они вполне могут существовать вместе. Например, агенты с определёнными ролями могут работать параллельно, а потом последовательно. Это нормальная практика в реальных системах.
Manager / Orchestrator
├─ Researcher: ищет факты и источники
├─ Analyst: делает выводы
├─ Writer: пишет понятный текст
└─ Reviewer: проверяет точность и полноту
Что такое субагенты в Claude Code ↘️
✅
Субагент — это всего лишь Markdown-файл с таким же YAML frontmatter, как и в скиллах, который лежит внутри настроек Claude Code. У него есть:
•	имя и описание
•	системная инструкция, которая подгружается при запуске
•	при необходимости — список доступных инструментов и скиллов
Субагенты удобно использовать для повторяемых ролей: ревьюер, тестировщик, исследователь, документатор, отладчик.
Главный агент никуда не исчезает. Если мы стартуем работу через него, он координирует субагентов: самостоятельно их запускает, выдаёт задачи, получает ответы и собирает финальный результат.
Настройки субагентов бывают двух типов:
•	Проектный уровень: .claude/agents/название-агента.md внутри папки проекта
•	Глобальный (пользовательский) уровень: ~/.claude/agents/название-агента.md
Инструменты для субагентов ↘️
Каждому субагенту можно выдать ровно те инструменты, которые нужны для его роли:
•	Read + Search — агенту-ревьюеру, который только читает файлы и выносит вердикт
•	Read + Search + Bash — если нужны терминальные команды (запросы к серверу, тестирование кода)
•	Read + Search + Bash + Edit — если агент ещё и исправляет файлы
💡
Если вы пока не уверены в выборе инструментов — выбирайте «все инструменты». Это снимает головную боль на старте, хотя в некоторых задачах чуть менее безопасно.
✅
Правило least privilege: если агент только проверяет результат, не даём ему право редактировать файлы. Если агенту не нужны команды терминала, не даём доступ к Bash.
Примеры уровней доступа:
Read, Grep, Glob — агент может провести ревью без правки файлов.
Read, Grep, Glob, Bash — агент может провести ревью и выполнить проверки через терминал.
Read, Grep, Glob, Edit, Bash — агент может проверять результат и исправлять файлы.
3. Первый запуск субагентов

Запуск субагентов без предварительной настройки ↘️
Начнём с простого примера. Открываем терминал, переходим в рабочую папку и запускаем Claude Code.
Первая команда — /agents. Она показывает запущенные субагенты и библиотеку всех доступных агентов на проектном и пользовательском уровнях.
Важный момент: субагентов можно использовать сразу, без предварительной настройки. Достаточно в запросе указать, что нужно запустить двух отдельных субагентов на разные темы — и Claude Code запустит их параллельно, потому что такова логика запроса.
Вы можете без лишних заморочек сразу начать работать с субагентами — просто скажите главному агенту, что нужно создать одного агента для такой-то задачи и второго для другой.
 
Напиши Claude Code следующий запрос:
Как работают субагенты в Claude Code? Запусти отдельного субагента-исследователя на эту задачу и запусти второго субагента на задачу: как связаны субагенты и скиллы внутри Claude Code.
Мы наблюдаем, как главный агент запустил двух субагентов параллельно, каждый использует инструменты, и в интерфейсе можно переключаться между ними при помощи стрелок. Когда субагенты завершают работу, главный агент агрегирует все результаты и возвращает нам финальный ответ.
💡
Быстрый запуск субагентов без ролей — удобный способ, но для более качественных результатов лучше создавать агентов с явными ролями и системными инструкциями.
4. Создание нового субагента

Создание нового субагента через интерфейс Claude Code ↘️
Чтобы создать нового агента через интерфейс:
1.	Вводим команду /agents
2.	Переходим в библиотеку (стрелка вправо)
 
3.	Выбираем Create new agent (Создать нового агента)
4.	Выбираем проектные настройки
 
5.	Выбираем Generate wuth Claude (Создать при помощи Claude)
6.	Описываем роль и задачи агента
Пример описания: «Субагент-ревьюер кодовой базы — смотрит на весь код в проекте и коротко по пунктам объясняет его логику для нетехнического человека, приводя аналогии».
Claude Code сам генерирует системные инструкции и создаёт файл внутри .claude/agents/. Далее нужно:
•	Выбрать инструменты (или выбрать «все инструменты»)
•	Выбрать модель: для простых задач подойдёт Haiku, либо inherit from parent — тогда субагент будет использовать ту же модель, что и главный агент
•	Настроить память агента: рекомендуется оставить Project scope
⚠️
После создания нового агента необходимо перезапустить Claude Code — не все настройки подтягиваются в текущую сессию автоматически.
Вызов субагента и экономия контекста ↘️
Субагента можно вызвать двумя способами:
•	Эксплицитно (явно, прямо, без намёков) — указать @имя-агента прямо в запросе
@codebase-explainer (agent) для @finance-card
•	Неявно — попросить главного агента выполнить задачу, и он сам решит, когда вызвать нужного субагента
Найди в моей директории проект «Файнанс карт» и сделай код-ревью для этого сайта. Используй субагента.
Зачем вообще делегировать задачи субагентам? Потому что это экономит контекстное окно главного агента.
Когда контекст заполняется, модель выполняет auto-compaction — сжимает всю предыдущую сессию до тезисов и «забывает» детали. Если мы делегируем тяжёлую работу (например, чтение большого количества файлов или ресёрч) субагенту, то расходуем его контекст, а главный агент получает лишь финальный вердикт и остаётся «чистым».
💡
Очень полезно делать все ресёрчи через субагентов. Если нужно найти документацию, собрать новости или прочитать блогпосты — запустите субагента для этой задачи. Главный агент (особенно если это дорогая модель типа Opus) останется с чистым контекстом и будет работать эффективнее. Это ещё и дешевле: дорогой Opus как главный агент + дешёвый Haiku как субагент для ресёрча.
5. Демонстрация работы субагента
Демонстрация: контент-завод на мультиагентной архитектуре ↘️
Разберём реальный пример — контент-завод, который берёт новость и превращает её в контент для соцсетей. Архитектура построена на скилле-оркестраторе и четырёх субагентах.
Скилл news2social v2 задаёт главному агенту роль оркестратора:
•	Принять один источник (ссылку или текст)
•	Параллельно запустить трёх субагентов: Content Writer, Image Generator, HyperFrames Agent
•	Собрать результаты в JSON-файл
•	Передать JSON агенту-Publisher для публикации в соцсети
Субагент Content Writer получает системные инструкции из предыдущей версии скилла — практически без изменений. Его задача: превратить источник в JSON со схемой постов для Telegram, Instagram, X и TikTok. Результат сохраняется в папку posts/.
Субагент Image Generator использует MCP fal.ai: формирует image-промпт, отправляет его в GPT Image 2, ждёт результата и сохраняет картинку. Важно: в инструкциях прописаны конкретные инструменты MCP — submit_job и check_job_status, чтобы агент не зависал.
Субагент HyperFrames генерирует видеоролик. В его frontmatter прописан ключ skills с названием скилла HyperFrames — так субагент получает всю информацию о том, как работать с этим инструментом.
Субагент Publisher работает на скилле Postis. Ему выданы только инструменты bash и read — он не может изменять файлы, только читать и отправлять команды.

Весь пайплайн в действии:
1.	Мы отправляем ссылку главному агенту.
2.	Он параллельно запускает Content Writer, Image Generator и HyperFrames Agent в фоновом режиме.
3.	Получает от них результаты и собирает JSON.
4.	Передаёт результат Publisherагенту, который публикует пост в X.
Мы просто скинули ссылку — и получили текст, картинку и видео, опубликованные в соцсети.
⚠️
В процессе демонстрации возникла ошибка: Content Writer создавал текст длиннее 200 символов для X. Агент сообщал об успехе, хотя на самом деле получал ошибку API. Это важный урок: коммуникацию между агентами нужно прописывать детально, включая форматы ошибок и критерии валидации. Можно добавить отдельный этап проверки длины или настроить хук.
💡
В пайплайне присутствуют все три модели коммуникации одновременно: три субагента работают параллельно, затем результаты собираются и передаются Publisher-агенту последовательно, и у каждого субагента есть своя чёткая роль.
6. Когда мультиагентность нужна — и как начать

Критерии выбора: один агент или система ↘️
Три главных признака того, что стоит задуматься о мультиагентной системе:
•	Объём задачи — задача большая и требует разных шагов
•	Повторяемость — процесс запускается регулярно
•	Типы работы — задача требует разных компетенций и инструментов
Если задача похожа на один короткий запрос — берём одного агента. Если задача похожа на процесс с разными этапами и компетенциями — появляется смысл в команде субагентов.
⚠️
Риск ошибок в мультиагентных системах велик — это нормально. Агенты могут возвращать формально «успешный» ответ при реальной ошибке, неэффективно расходовать контекст или создавать лишнее. Задача агентного инженера — это увидеть и итерационно поправить.
Вопросы для проектирования своей системы ↘️
Прежде чем строить мультиагентную систему, ответьте на эти вопросы:
•	Что мы хотим получить на выходе?
•	Какие этапы нужны, чтобы получить этот результат?
•	Какие навыки и инструменты нужны для каждого этапа?
•	Какие этапы можно отдать отдельным агентам, а какие — главному?
•	Как один агент передаёт результат следующему?
•	Как проверяется качество финального результата?
💡
Для передачи результатов между агентами лучше всего использовать JSON — это чёткий контракт, который все агенты понимают одинаково.
Рекомендации для старта ↘️
Начинайте с дуэта: главный агент + один субагент с конкретной ролью и ограничениями.
Полезная последовательность:
1.	Сначала реализуйте задачу вручную через одного агента — так вы поймёте весь процесс и все input/output
2.	Перенесите эту логику на взаимодействие главного агента и субагента
3.	Итерационно улучшайте: уточняйте роли, форматы передачи результатов, критерии качества
4.	Следите не только за финальным результатом, но и за логами взаимодействия агентов
Для каждой роли важно зафиксировать: цель, вход, выход и критерий качества.
Мультиагентная система нужна не всегда. Её смысл — разделить разные типы работы между ролями и усилить автоматизацию. Для старта достаточно дуэта. Главный критерий: стал ли результат качественнее, понятнее и стабильнее.
Дополнительные материалы
Словарь занятия ↘️
•	Мультиагентная система — архитектура, в которой несколько AI-агентов взаимодействуют для решения сложной задачи
•	Оркестрация — процесс управления работой нескольких субагентов главным агентом
•	Главный агент (оркестратор) — агент, который координирует субагентов, выдаёт им задачи и собирает результаты
•	Субагент — Markdown-файл с системной инструкцией и настройками, который запускается внутри текущей сессии Claude Code
•	YAML frontmatter — блок метаданных в начале Markdown-файла, содержащий имя, описание, модель и инструменты агента
•	Последовательная модель — агенты выполняют задачи цепочкой, каждый следующий зависит от результата предыдущего
•	Параллельная модель — несколько агентов работают одновременно над разными частями одной задачи
•	Ролевая модель — каждому агенту заранее назначена чёткая роль (ресёрчер, аналитик, райтер, ревьюер)
•	Контракт агента — чёткий формат (обычно JSON), в котором агент принимает данные и возвращает результат
•	Контекстное окно — ограниченный объём памяти модели в рамках одной сессии
•	Auto-compaction — автоматическое сжатие истории сессии, когда контекстное окно заполняется
•	Inherit from parent — настройка модели субагента, при которой он использует ту же модель, что и главный агент
•	Project scope — область памяти агента, ограниченная текущим проектом
•	Dry run — тестовый запуск без реального выполнения финального действия (например, публикации)
•	Pipeline — последовательность шагов обработки данных от входа до результата
